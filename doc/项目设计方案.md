## 1. 项目目标

在 `my-coding-agent/` 中独立实现一个面向本地代码仓库的 coding agent。它通过 Anthropic-compatible Messages API 模型进行多轮对话，可以自主读取文件、提出文件修改、执行命令并根据结果继续工作，使用体验对齐 Codex、OpenCode 一类 coding agent，而不是一次性聊天机器人。

项目必须自行实现以下核心逻辑：

- 对话历史、会话恢复与动态上下文管理；
- 模型流式输出及 tool call 的语义聚合与校验；
- 工具定义、审批和本地执行；
- Agent Loop、轮次上限与循环终止；
- 用户停止、网络重试、错误分类和服务重启恢复；
- 前后端状态同步与可审计事件。

允许使用官方 `anthropic` Python 客户端完成 HTTP、认证、SSE 帧解析和基础对象反序列化，但不使用 Claude Agent SDK 或任何其它 Agent 框架，也不依赖 Anthropic server tools、code execution 等服务端托管工具。

## 2. 设计原则与范围

### 2.1 设计原则

1. **本地执行**：文件和命令工具全部由本机后端执行。
2. **历史保真**：压缩只改变发给模型的临时视图，不删除或改写原始历史。
3. **副作用可控**：读文件自动执行；写文件和运行命令默认逐次审批。
4. **状态可解释**：每次运行、审批、重试、工具结果和停止原因均可追踪。
5. **协议边界清晰**：符合 Anthropic Messages API、Messages SSE 和 client tool use 语义的服务可通过配置切换；Agent Core 只处理厂商无关语义对象，不接触 Anthropic wire payload。
6. **范围克制**：先完整实现一道可靠的 Agent 主链路，再优化视觉和扩展功能。

### 2.2 P0：截止前必须完成

- React + TypeScript + Vite 网页端；
- Python 3.12 + FastAPI 本地后端；
- 运行环境为 macOS/Linux 等 POSIX 系统；Windows 进程组语义不在 P0 保证范围；
- `uv` 作为唯一 Python 环境、依赖和运行入口；
- 多轮会话及 SQLite 持久化；
- 单进程、全局最多一个活动 run；
- `read_file`、`write_file`、`run_command`、`skill` 四个模型可见工具（`skill` 为按需加载工作区技能的只读工具，见 §10.5）；
- Anthropic-compatible Messages API 流式输出；
- 网页选择工作目录，以及启动时通过 `--workspace` 指定初始目录；
- 写入和命令审批、`--yes` 受信任模式；
- Stop、限流与网络重试、刷新重连，以及服务重启后“不重放副作用”的保守恢复；
- **上下文预算、确定性 tool-output 裁剪和同步 LLM 摘要压缩**，原始历史始终保留；
- 正式 headless 入口、基础运行报告、4 个公开小任务各 1 次的轻量 smoke；
- 默认离线的核心测试、至少 1 条完整网页 E2E 和 1 条 Stop E2E；
- 公开仓库、README.md、1000 汉字内 README.txt、2 分钟内 MP4、最终 zip 与表单提交核验。

### 2.3 P1：P0 稳定后再完成

- `pause_turn` 自动 continuation、`stream=false` 兼容模式和额外 provider 扩展；
- Session 重命名/删除、JSONL 导出、复杂响应式视觉优化；
- 更完整的服务重启/并发竞态矩阵与非对抗性路径边界之外的 dirfd/`O_NOFOLLOW` 加固；
- 12 个自建任务 × 3 次正式 campaign、压缩消融和完整统计报告；
- 固定 3 个 SWE-bench Verified 实例及其它外部 benchmark smoke。

### 2.4 明确不做

- 多个 run 并发执行；
- 多 Agent、子 Agent、规划器或工作流引擎；
- LangChain、LlamaIndex、OpenAI Agents SDK、Claude Agent SDK、AutoGen、CrewAI、MCP SDK 等框架；
- OpenAI Chat Completions、Responses API 等第二套协议；
- Anthropic server tools、extended thinking、beta headers 和其它首版不需要的私有扩展；
- Code Interpreter、Files API 或其它服务端执行/文件能力；
- RAG、向量库、代码索引和插件系统；
- 独立的 search、grep、edit 或 patch 工具；
- PTY、交互式 stdin、后台 job；
- 产品内置容器或真正的命令沙箱；P1 评测 harness 可在产品外部使用一次性容器隔离无人值守运行；
- 内置代码编辑器、完整终端或 IDE 工作台；
- 远程部署、用户登录和权限账户系统。
- 评测排行榜、Web dashboard、自动生成任务和 LLM-as-judge 主观评分。

## 3. 核心术语

- **Session**：一段可持久恢复的多轮对话，创建时永久绑定一个 workspace。
- **Run**：用户发送一条消息后，到本次 Agent 工作结束、失败或被停止的完整过程。
- **Round**：一次模型调用。一次 run 可以包含多次“模型 → 工具 → 模型”。
- **Tool call**：模型在 assistant 响应中提出的一次工具调用。
- **Committed message**：完整解析、通过结构校验且相关工具结果已配对，可安全参与后续上下文的消息。
- **Draft**：流式过程中用于 UI 展示的临时文本；中断后不得进入模型上下文。
- **Model view**：Context Builder 针对当前模型窗口临时生成的 messages，不等同于数据库中的完整历史。
- **Durable event**：已写入 SQLite、带单调递增序号、可在重连后补发的事件。

## 4. 总体架构

采用事件驱动的模块化单体：一个 FastAPI 进程、一个 React 应用、一个 SQLite 数据库，不引入 Redis、消息队列或进程间 RPC。

```text
React Workbench
    │  REST：启动、查询、目录与会话管理
    │  WebSocket：发起 run、审批、停止与实时事件
    ▼
FastAPI API / WS Gateway
    ▼
Run Coordinator ── Session Service ── Event Publisher
    ▼
Agent Loop
    ├── Context Builder / Compactor
    ├── Anthropic-compatible Messages Model Adapter
    ├── Approval Gate
    ├── Tool Registry / Tool Executors
    └── SQLite Session Store
```

依赖约束：

- 前端只渲染后端状态，不自行推断 Agent 状态机；
- API 层只负责协议校验和转发，不包含 Agent 决策；
- Agent Loop 依赖模型、上下文、工具和存储接口，不依赖 FastAPI；
- 工具执行器不依赖模型 SDK、SQLite 或 Web UI；
- Model Adapter 不访问 workspace；
- Agent Core 和 SQLite 保存厂商无关的 user/assistant/tool 语义；只有 Model Adapter 将其转换为 Anthropic content blocks；
- SQLite 是唯一权威状态，不和 JSONL 双写；
- JSONL 仅作为用户主动导出的会话格式。

## 5. Run 状态机与事件

### 5.1 状态

Run 使用以下状态：

```text
STARTING
   ↓
BUILDING_CONTEXT ←→ COMPACTING（需要时）
   ↓
MODEL_STREAMING ←→ RETRY_WAIT
   ├── 正常结束且无工具 ───────────→ COMPLETED
   ↓ 有工具
AWAITING_APPROVAL（read_file 跳过此状态）
   ↓
TOOL_RUNNING
   └──────────────────────────────→ BUILDING_CONTEXT

任意活动状态 ── Stop 已持久化接受 ─→ CANCELLING ─→ CANCELLED

其它终态：STOPPED / CANCELLED / FAILED / INTERRUPTED
```

Session 通常由是否存在活动 run 决定能否接受新消息；`CANCELLING` 仍是活动状态。终态 run 结束后，Session 回到 `IDLE`，但 `requires_recovery_ack=true` 时仍禁止新 Run，直到用户确认已检查未知副作用。全局若已有活动 run，另一个 Session 的发送请求应被明确拒绝，而不是排队或并行执行。

除图中的正常边外，任意活动状态只能依据明确的 stop reason 转入对应 `STOPPED`/`FAILED`/`INTERRUPTED` 终态；所有终态不可迁出。状态更新使用 expected-state 条件更新，失败时重新读取当前状态，禁止迟到的模型、审批或工具结果覆盖终态。

### 5.2 停止原因

Run 状态与停止原因分离。停止原因至少包括：

- `COMPLETED`
- `USER_STOP`
- `MAX_ROUNDS`
- `DOOM_LOOP`
- `EMPTY_RESPONSE`
- `OUTPUT_TRUNCATED`
- `INCOMPLETE_TOOL_CALL`
- `AUTH_ERROR`
- `CONFIG_ERROR`
- `RETRY_EXHAUSTED`
- `CONTEXT_OVERFLOW`
- `MODEL_REFUSAL`
- `PAUSE_TURN`
- `SERVER_RESTART`
- `MODEL_PROTOCOL_ERROR`

调用方和前端不得从自然语言错误中猜测停止原因。

终态和停止原因是两个字段：正常完成使用 `state=COMPLETED, stop_reason=COMPLETED`；预算、防循环、模型拒绝或 P0 不支持的 `pause_turn` 使用 `state=STOPPED`；用户主动停止使用 `state=CANCELLED, stop_reason=USER_STOP`；服务重启遗留运行使用 `state=INTERRUPTED, stop_reason=SERVER_RESTART`；认证、配置、上下文超限和重试耗尽等不可恢复错误使用 `state=FAILED`。

### 5.3 事件提交规则

- 创建 run、提交完整 assistant 消息、请求/处理审批、开始/结束工具、安排重试和结束 run 都先事务性写入 SQLite，再发布给前端。
- Stop 与工具副作用启动共享同一 Coordinator 临界区和条件更新：`begin_effect` 只有在 Run 仍活动且尚未请求取消时才能把工具标记为 running；Stop 先持久化取消请求并进入 `CANCELLING`。两者只能有一个先取得线性化点。
- `assistant.delta` 和 `tool.output.delta` 是高频瞬时事件，不逐片写入数据库。
- SQLite 中的 durable event 使用单调递增 `seq`。
- 浏览器重连时在同一 SQLite read transaction 中取得 Session 投影和 `snapshot_seq`；前端应用 snapshot 后把 `last_seq` 设为该值，只再接受 `seq > snapshot_seq` 的 durable event。订阅注册与 snapshot cut 由 session 级 publisher lock 串行化，握手期间的新事件先缓冲，避免查询与 live 订阅之间漏事件。
- 若后端进程仍存活，快照可以包含当前内存 draft；若后端已重启，draft 丢弃并将原 run 标记为 `INTERRUPTED`。

### 5.4 运行状态与任务阶段分离

Run 状态只表达后端可观察、可持久化和可恢复的运行事实，例如正在构建上下文、等待模型、等待审批或执行工具。`plan`、`execute`、`verify`、`reflect` 不加入 Run 状态枚举，也不与这些运行状态做笛卡尔组合，原因是它们可能被跳过、交错或重复，而且不能从模型的自然语言或隐藏推理中可靠判定。

前端同样只展示有证据的状态，例如“正在读取文件”“等待写入批准”“正在运行测试”“等待重试”，不猜测模型当前是否正在规划或反思。若以后加入独立 Plan mode，它应是改变提示词与工具权限的可选运行模式，而不是每个任务必须经过的生命周期阶段。

## 6. SQLite 持久化

SQLite 位于用户数据目录，默认使用 `~/.my-coding-agent/state.db`，不写入目标 workspace 或公开仓库。启用 foreign keys、WAL 和合理的 busy timeout。

核心表：

### `sessions`

- `id`
- `title`
- `workspace_realpath`
- `requires_recovery_ack`
- `created_at`
- `updated_at`

### `runs`

- `id`
- `session_id`
- `state`
- `stop_reason`
- `error_kind`
- `cancellation_requested_at`
- 不含密钥的模型配置快照
- input/output/cache creation/cache read usage、轮次和重试统计
- 最近一次上下文构建的只读估算投影（estimated/available/window 及静态预算字段，见 §7.1；仅活动 run 可更新）
- `started_at`、`finished_at`

### `messages`

- `id`
- `session_id`
- `run_id`
- 会话内递增 `seq`
- `role`
- 厂商无关的有序文本/tool-use/tool-result payload；assistant 的 text/tool-use block 相对顺序必须保真
- `status = pending_tools | committed | interrupted`
- 可选 `tool_call_id`

### `model_requests`

- `id`、`run_id`、`round_no`
- `kind = main | compaction`
- 模型标识和不含密钥的请求配置 hash
- 开始/结束时间、结果和 attempt 数
- input、output、cache creation、cache read token usage 及 `usage_source`
- 网络重试次数与累计等待时间

### `tool_executions`

- `tool_call_id`
- `assistant_message_id`
- 调用顺序、名称、冻结后的参数
- 审批状态和决定时间
- `effect_started_at`，用于区分尚未发生副作用和可能已经发生副作用
- 写文件基线 hash
- 执行状态、结果 envelope、耗时

### `context_snapshots`

- 覆盖到的消息序号
- 结构化滚动摘要
- 生成摘要时的模型配置与 token 估算

### `events`

- `seq`
- `session_id`、`run_id`
- `type`
- JSON payload
- `created_at`

### `client_commands`

- `session_id`
- 唯一的 `client_command_id`
- 命令类型
- canonical payload hash
- `status = processing | completed`
- 已创建的 resource ID、首次 ACK 或对应事件序号
- `created_at`

关键不变量：

- 含 tool calls 的 assistant 消息先以 `pending_tools` 保存并创建待执行记录；此时可供 UI 和恢复逻辑读取，但不得进入模型上下文；
- 每个 tool call 都得到恰好一条内部 `role=tool` 结果后，在同一事务中把整个 assistant/tool 组转为 `committed`；wire 格式由 Adapter 另行转换；
- 拒绝、取消、参数错误和未执行的同批调用也用 tool result 补齐；
- assistant 流未完整结束时，不提交正式 assistant/tool-call 消息；
- 所有工具副作用和对应状态必须以事务边界清晰地记录；
- 导出 JSONL 是对 SQLite 的只读投影，不成为第二事实源。

## 7. 上下文管理与压缩

### 7.1 预算

```text
available_input_tokens =
    context_window
    - max_output_tokens
    - safety_margin_tokens
```

默认配置：

- `compact_trigger_ratio = 0.80`
- `compact_target_ratio = 0.60`
- `safety_margin_tokens = 2048`
- 至少保留最近 2 个用户发起的完整轮次；
- 最近完整轮次尽量占可用输入预算的 35%–40%。

Messages API 没有可供所有 Anthropic-compatible 服务统一查询的模型窗口元数据，因此 `context_window` 和 `max_output_tokens` 必须显式配置。请求前使用 `ceil(UTF-8 字节数 / 3)` 加协议固定开销作为**启发式估算**，不能把它宣称为 token 上界；测试覆盖高熵 ASCII、代码和转义 JSON，运行时记录 estimate 与 API usage 的误差用于校准。Provider 返回结构化 context-too-large 错误时，仍触发一次压缩重建作为最终保护。

### 7.2 不可压缩内容

以下内容在每次模型视图中都必须原样保留：

- System/developer 指令、工具 schema 和当前环境信息（含工作区 `AGENTS.md` 注入的 workspace 指令小节与技能索引，见 §10.5）；
- **Session 中所有 `role=user` 输入的原文、顺序和角色**，不摘要、不截断、不改写；
- 当前 run 中已经 committed、尚未纳入摘要的完整 assistant/tool 组；
- 最近至少 2 个用户发起的完整轮次。

`pending_tools` 或流式 draft 只供 UI、审批和恢复使用，绝不进入模型视图，也不计入下一次模型请求的 mandatory 内容；只有补齐全部 tool results 并原子转为 committed 后才可参与 Context Builder。

最初需求不再作为一份额外副本重复插入，因为它已经包含在“所有用户输入”中。rolling summary 可以辅助标注较新要求覆盖较旧要求，但不能替代任何用户原文；P0 不维护独立的语义约束账本。

### 7.3 模型视图

Context Builder 从 canonical transcript 生成如下投影：

1. System/developer 指令、工具 schema 和当前环境；Model Adapter 最终将 system/developer 指令编译到 Anthropic 顶层 `system`，不会伪造 `system`/`developer` role message；
2. 已退出 active zone 的历史 user 消息，逐条保持原始 `role=user` 与原文；
3. 一份当前 rolling summary，只归纳被省略的旧 assistant/tool 行为，并注明覆盖的事件序号；摘要可列出当前约束，但不能替代或改写任何 user 原文；
4. 最近完整原始轮次，其中 user、assistant、tool calls 和 tool results 均保留；
5. 当前用户消息及当前 run 已完成的工具往返。

同一条用户消息只出现一次。模型视图只选择 committed 消息；内部的 assistant tool-use 与对应的全部 tool results 是不可拆分的原子组，必须整体保留或由摘要整体替代。内部 canonical `role=tool` 只是厂商无关语义，Adapter 会把同批结果编译为紧随 assistant `tool_use` 的 Anthropic `role=user` + `tool_result` content blocks，不能把数据库 role 直接作为 wire role。

### 7.4 压缩流程

1. 先计算 mandatory budget：system/developer、工具 schema、环境、所有 user 原文、当前 run 已 committed 的未摘要工具往返和最近完整轮次；display-only 的 ThinkingPart 与模型视图一样不计入该预算与压缩请求预算（见 §8.2），而 tool_use 参数属于真实模型视图内容、照常计入。
2. 若 mandatory 内容已经超过可用输入预算，直接返回 `CONTEXT_OVERFLOW`，不调用模型，也不牺牲用户原文。
3. 估算完整模型视图；达到可用预算 80% 时触发压缩。
4. 首先确定性瘦身较早的大块 tool output，在模型视图中替换为包含工具名、状态、目标、大小和摘要的占位说明。
5. 压缩请求单独计算 `compaction_input_budget = context_window - summary_max_tokens - safety_margin - system/protocol_overhead`；任何摘要 chunk 都必须在发送前落入该预算。
6. 若仍超预算，将更早的完整 assistant/tool 组连同其关联 user 原文作为只读语境，序列化为转义后的 JSON，再交给一次禁用 tools 的模型调用生成结构化摘要；输出只归纳 assistant/tool 行为，user 原文仍在正式模型视图中逐条保留。摘要输入过大时按完整组分块处理，避免未转义 XML/标签边界被代码内容破坏。
7. 摘要至少包含：已完成工作及证据、重要文件/符号、工具调用结论、关键命令与测试结果、失败尝试、未完成事项、阻塞和下一步。用户要求可以引用，但不由摘要替代。
8. 新摘要替换旧 rolling summary，而不是追加到用户消息；snapshot 记录版本、来源事件 ID、模型、估算器和 token 数。
9. 新摘要作为独立 snapshot 写入 SQLite，不覆盖原消息；空摘要、格式错误、超出摘要预算或请求失败时继续使用上一有效快照。
10. 60% 是软目标而不是硬不变量：`target_tokens = max(0.60 × available_input_tokens, mandatory_tokens)`。若该目标不超过 available budget，尽量压到目标；若 mandatory 已高于 60% 但仍可放入窗口，则返回最小合法视图并记录 `compaction_above_target=true`；只有超过 available budget 才返回 `CONTEXT_OVERFLOW`。

切换到更小上下文窗口的模型时，从 SQLite 完整历史和现有摘要重新计数并重建视图。若不可压缩内容仍超限，UI 提示用户切换更大窗口模型或创建新 Session；系统不得自动删除用户输入。

强制触发：`session.compact`（§14）与 provider 返回结构化 context-too-large 后的一次性重建，都复用同一 plan 构造但把触发阈值视为已越过——不管当前估算是否达到 80%，只要有可替换的完整 assistant/tool 组就生成压缩计划；无可替换组（全部 mandatory 或已超 available budget）时分别以 `COMPACTION_NOT_POSSIBLE` / `CONTEXT_OVERFLOW` 命令错误拒绝，而不静默成功。

### 7.5 OpenCode Review 的启发与边界

参考实现固定为公开仓库 `alibaba/open-code-review` 的 `b17460a6`：

- 它使用 60% soft threshold 异步压缩、80% warning threshold 同步压缩；
- 把前两条消息作为 frozen zone，把 assistant 及其连续 tool results 组成完整 round，再划分 compress/active zone；
- 独立 LLM 请求生成摘要；失败或空摘要时保留原消息；
- 异步任务使用会话级状态、消息快照、`snapshotLen` 后缀合并、job ownership 检查、取消与结束前 join。

这些模式启发了本项目的完整轮次边界、失败不破坏历史、summary snapshot 和未来异步压缩的 revision/CAS 设计。源码参考：[阈值与分区](https://github.com/alibaba/open-code-review/blob/b17460a6a3de8c5f93f693a1f3a0a17a77ed452c/internal/llmloop/compression.go#L19-L156)、[同步摘要](https://github.com/alibaba/open-code-review/blob/b17460a6a3de8c5f93f693a1f3a0a17a77ed452c/internal/llmloop/compression.go#L208-L284)、[异步任务](https://github.com/alibaba/open-code-review/blob/b17460a6a3de8c5f93f693a1f3a0a17a77ed452c/internal/llmloop/compression.go#L287-L379)和[主循环触发点](https://github.com/alibaba/open-code-review/blob/b17460a6a3de8c5f93f693a1f3a0a17a77ed452c/internal/llmloop/loop.go#L709-L760)。

不直接复制其实现，原因包括：

- 固定冻结前两条消息及只识别 assistant/tool round，不适合多轮 user 输入；
- token 统计只读取 message text，没有覆盖 tool-call arguments、工具 schema 和完整协议开销；
- 摘要追加到初始 user message，会让多次摘要累积；
- XML 包装未转义，不适合直接承载任意代码和工具输出；
- `prevSummaryTokenEstimate` 在当前调用路径中始终为 0，没有真正预留摘要预算；
- soft-threshold 路径存在注释/实现不一致：分区函数称全部 round 可容纳时“不需要压缩”，却返回 `compressEnd=len(messages)`，随后实际压缩全部非冻结消息，且现有测试未覆盖这一真实触发组合。

因此 P0 坚持同步压缩：80% 触发，先 prune，再以 60% 为软目标生成独立摘要。异步压缩只作为后续性能优化；若引入，必须使用 conversation revision、来源事件 ID、模型/估算器身份和单一 job ownership，禁止过期结果覆盖新上下文。

## 8. Anthropic-compatible Messages Model Adapter

### 8.1 SDK 边界

使用官方 `anthropic` Python SDK 的 `AsyncAnthropic` 和 Messages API：

- SDK 负责 HTTP、认证、连接池、SSE 帧解码、JSON 反序列化和基础异常类型；
- SDK 初始化时设置 `max_retries=0`；
- 项目自行实现请求重试、Messages event/content-block 语义聚合、tool-use 校验、Agent Loop 和全部本地工具行为；
- 不使用 Claude Agent SDK 或任何其它 Agent 框架；
- 不调用 web search、code execution、computer use 等 Anthropic server tools。

模型配置包含 `base_url`、`model`、API key 环境变量名、上下文窗口、输出预算和流式开关。`base_url` 表示 SDK API 根地址，例如 `https://api.anthropic.com`，不手工追加 `/v1/messages`。兼容基线为 `anthropic-version: 2023-06-01`；该请求头由 SDK 负责，不在首版开放任意 header 或 beta 配置。适配范围是标准 Anthropic Messages API + client tools，不承诺兼容偏离协议、缺失 tool use 或依赖私有扩展的服务。

协议细节以 Anthropic 官方 `anthropic-sdk-python` v1.1.0（commit `181e2e57`）生成的公开类型为核对基线：[Messages 请求](https://github.com/anthropics/anthropic-sdk-python/blob/181e2e5715c89a1451e384adb01d70a59d3ca10d/src/anthropic/types/message_create_params.py#L36-L203)、[流式事件](https://github.com/anthropics/anthropic-sdk-python/blob/181e2e5715c89a1451e384adb01d70a59d3ca10d/src/anthropic/types/raw_message_stream_event.py#L14-L27)和[停止原因](https://github.com/anthropics/anthropic-sdk-python/blob/181e2e5715c89a1451e384adb01d70a59d3ca10d/src/anthropic/types/stop_reason.py#L7-L9)。

正常轮次只发送可移植的必要字段：`model`、必填的 `max_tokens`、顶层 `system`、`messages`、四个 `{name, description, input_schema}` 工具定义、`tool_choice={"type":"auto"}` 和流式开关。最后一轮强制总结和压缩请求同时省略 `tools` 与 `tool_choice`。请求不携带 `thinking` 字段，字段集对推理保持中性：是否开启推理由服务端默认决定（例如阿里云百炼的 Qwen 默认思考，Anthropic 官方默认不思考）；服务端返回的 thinking block 按 8.2 聚合展示。首版不请求启用 extended thinking，也不发送 prompt caching、service tier 或 beta 字段。

内部历史与 wire payload 严格分层：

- system/developer 指令和环境说明编译到顶层 `system`；Messages API 的 `messages` 中不存在 `system` 或 `developer` role；
- 人类输入映射为 `role=user` 的 `text` block；
- assistant 文本与工具请求按原始顺序映射为同一 `role=assistant` 消息中的 `text`/`tool_use` blocks；`tool_use` 保存原始 `id`、`name` 和对象类型 `input`；
- 同批本地工具结果合并为紧随其后的一个 `role=user` 消息，内容是按调用顺序排列的 `tool_result` blocks，以 `tool_use_id` 配对，失败结果设置 `is_error=true`；
- 相邻同 role 的 wire 消息在不跨越 tool-use/result 原子边界的前提下合并 content blocks；Core 与 SQLite 继续使用厂商无关的 user/assistant/tool 语义。

### 8.2 流式语义聚合

SDK Messages SSE event 归一化为内部 `AssistantTurn`：

- `message_start` 初始化 message identity 和输入/cache usage，重复或缺失均为协议错误；
- `content_block_start` 按 `index` 建立并锁定 `text`、`tool_use` 或 `thinking` block；其余未知 block 类型在首版返回 `MODEL_PROTOCOL_ERROR`。`thinking` block 的文本经 `thinking_delta` 按 block 聚合为仅供展示的 `ThinkingPart`，按原始 block 顺序进入 `AssistantTurn` 并随消息持久化；流式期间以瞬态事件（`assistant.thinking.delta`/`assistant.thinking.closed`）推送 UI 折叠展示，不写入 events 表；`signature_delta` 消费后丢弃；thinking 从不回传给模型（模型视图、token 估算与 wire 编译均跳过）；index 冲突或未关闭仍是协议错误；
- `text_delta` 追加到对应文本 block，并把增量推送 UI draft；
- `input_json_delta.partial_json` 只追加到对应 tool-use block，不在 block/message 结束前解析或执行；
- `content_block_stop` 封闭指定 block；index、block 类型、tool-use ID/name 冲突或缺失均为协议错误；
- `message_delta` 保存最终 `stop_reason` 和累计 output usage，usage 取最终累计值而不是逐事件相加；
- `message_stop` 是完整流的必要终点；`ping` 可忽略，流内 `error` 转成模型传输错误；
- 完整结束后统一解析每个 tool-use input JSON 并执行本地 schema 校验；多个 `text`/`thinking`/`tool_use` blocks 保持原始顺序。

P0 固定 `stream=true`；配置中的 `stream` 用于显式记录并校验该约束。`stream=false` 及非流式 `Message` 归一化属于 P1。

usage 保留 `input_tokens`、`output_tokens`、`cache_creation_input_tokens` 和 `cache_read_input_tokens` 四个原始组成项；缺失值记为 `null`。不得把流式累计 usage 相加，也不得把本地估算冒充 API usage。

### 8.3 特殊输出

- 空文本且无工具：语义重试一次；再次为空则以 `state=STOPPED, stop_reason=EMPTY_RESPONSE` 结束。
- 参数是完整但非法的 JSON：若 call id 和名称有效，提交对应 tool error，最多允许模型连续自纠 2 次。
- `stop_reason=end_turn|stop_sequence` 且无工具：提交最终文本并正常完成；若存在完整 client `tool_use` blocks，则实际工具块优先并继续循环，同时记录 stop-reason 不一致诊断。
- `stop_reason=tool_use`：只有全部 tool-use blocks 完整且参数合法时才进入工具阶段；没有 tool-use block 则为 `MODEL_PROTOCOL_ERROR`。
- `stop_reason=max_tokens` 且响应含任意 tool-use block：无论当前 JSON 看起来是否完整，都记为 `INCOMPLETE_TOOL_CALL`，不执行、不进入普通网络重试，也不将该调用提交到正式消息历史。
- `stop_reason=max_tokens` 且只有文本：保留并展示截断文本，以 `OUTPUT_TRUNCATED` 结束，不把它误报为正常完成。
- `stop_reason=pause_turn`：P0 不做 provider continuation；保存 UI 可见诊断但不进入模型上下文，以 `STOPPED/PAUSE_TURN` 结束。自动 continuation 及其持久化/恢复属于 P1。
- `stop_reason=refusal`：保留可展示文本，以 `STOPPED/MODEL_REFUSAL` 结束，不当作网络错误重试。
- `stop_reason=model_context_window_exceeded`：先压缩并重建一次模型视图；仍超限则以 `FAILED/CONTEXT_OVERFLOW` 结束。
- 未知 stop reason、缺少 message/block 必要终止事件、缺少 tool-use ID/name 或同一 index 身份冲突均记为 `MODEL_PROTOCOL_ERROR`。

错误边界固定如下：SDK 抛出的 `APIConnectionError`、`APITimeoutError` 和 `APIStatusError` 子类属于传输/API 错误，只有满足第 12.2 节白名单时才重试；Anthropic-compatible 服务以结构化 error type/code 返回 context-too-large 时，只允许触发一次压缩重建，不能靠自然语言 message 猜测。HTTP 请求成功后出现的 event/block 顺序冲突、缺少必要字段或无法形成合法 `AssistantTurn` 属于模型协议错误，不做网络重试。参数 JSON 完整但不符合工具 schema 则属于可回灌的工具参数错误，不与前两类混淆。

## 9. Agent Loop

### 9.1 主循环

单次 run 的主流程：

1. 事务性保存 user message，创建 run 和取消令牌；
2. Context Builder 生成当前模型视图，必要时先压缩；
3. 经 Model Adapter 流式调用模型；
4. 完整聚合并校验 `AssistantTurn`；
5. 先处理 `max_tokens`、`pause_turn`、`refusal` 和 context overflow 等特殊 stop reason；
6. 正常结束且无 tool use 时，原子提交 assistant 消息并以 `COMPLETED` 结束；
7. `stop_reason=tool_use` 且存在完整 tool use 时，将 assistant 和调用记录持久化为 `pending_tools`；
8. 按原始顺序逐个校验、审批、执行并补齐内部 tool result；全部调用都有结果后，将整个组原子转为 `committed`；
9. Adapter 将同批结果编译成一个 Anthropic user/tool-result message，重新进入 Context Builder 和下一次模型调用。

`round` 明确定义为一次模型调用。`max_rounds` 默认 30，可在配置文件中调整：

- 第 1 到 `max_rounds - 1` 次模型调用正常提供工具；
- 只有前序调用仍要求工具时，才进入第 `max_rounds` 次调用；
- 最后一次调用不提供 tools，并追加“直接总结当前结果”的指令；
- 最后一次文本可展示并保存，run 以 `state=STOPPED, stop_reason=MAX_ROUNDS` 结束；
- 若模型在没有工具定义时仍输出工具调用，不执行或提交该调用；原始响应只保存为诊断事件，并以 `state=STOPPED, stop_reason=MAX_ROUNDS, error_kind=MODEL_PROTOCOL_ERROR` 结束。

循环防护：对工具名和 canonical JSON 参数计算稳定指纹。默认阈值 3 表示前两次照常执行；模型第三次连续提出相同调用时不再执行，而是回灌 `repetition_detected` tool error；下一轮若仍提出相同调用，则以 `state=STOPPED, stop_reason=DOOM_LOOP` 结束。

### 9.2 软工作流程与验证策略

Agent 采用统一工具循环，而不是强制的 `PLAN → EXECUTE → VERIFY → REFLECT` 有限状态机。System prompt 约束模型按任务需要执行以下工作方式，但允许简单问答、小修改或无法验证的任务跳过不适用步骤：

```text
理解与必要规划 → 读取/修改/执行 → 查看工具证据 → 调整或重试 → 尽可能验证 → 最终回复
                                      ↑_________________________|
```

- **Plan**：复杂任务应先检查相关文件并形成简短计划；简单任务可以直接执行。计划是模型的工作记忆或可展示文本，不是完成条件，首版不增加 `update_plan` 工具。
- **Execute**：实际行为统一表现为 `read_file`、`write_file` 和 `run_command`，仍受路径边界、审批与取消规则控制。
- **Verify**：发生修改后，prompt 要求模型在可行时运行范围最小且相关的测试、构建或静态检查。验证证据来自真实 `run_command`、退出码和输出，而不是模型声称“测试已通过”。若没有可用测试、命令被用户拒绝或环境阻塞，允许正常回复，但必须明确说明未验证内容。
- **Reflect**：工具失败、测试失败或结果不符合预期时，将结构化结果回灌下一轮，由模型检查原因、修正方案并按需再次执行；它是循环中的行为，不是独立持久状态。服务端返回的推理输出按 8.2 聚合持久化并在 UI 中默认折叠展示（所有者决策），但从不进入模型上下文，也不驱动任何状态转移。
- **Finish**：首版不增加模型可见的 `complete`/`task_done` 工具。只有完整、合法、非截断的 assistant 响应不含 tool calls 时，宿主才产生内部 `Complete` outcome；若文本和 tool calls 同时存在，仍先执行工具并继续循环。

`state=COMPLETED` 仅表示 Agent Loop 正常收束，不表示代码已被客观证明正确。UI 展示实际执行过的验证命令及结果；评测则另以 `artifact_correct` 和 `strict_success` 判定产物正确性。计划项、自然语言“已完成”以及模型内部反思均不得直接驱动状态转移。

该决策参考了三类公开实现：Codex CLI `0.150.1` 使用 `Plan/Default` 模式、计划事件和统一 model/tool loop，而非四阶段状态机（[模式定义](https://github.com/openai/codex/blob/90854393966b21e9ebfd21b122334eb09a20c93d/codex-rs/protocol/src/config_types.rs#L673-L702)、[循环判定](https://github.com/openai/codex/blob/90854393966b21e9ebfd21b122334eb09a20c93d/codex-rs/core/src/session/turn.rs#L397-L562)）；OpenCode `6568a824` 的 plan/build 主要由 agent 配置、权限和提示词实现，todo 不控制循环（[Plan mode](https://github.com/anomalyco/opencode/blob/6568a824553200254e30e5a49c2831d1fb5f62e2/packages/opencode/src/session/prompt/plan-mode.txt#L8-L69)、[循环判定](https://github.com/anomalyco/opencode/blob/6568a824553200254e30e5a49c2831d1fb5f62e2/packages/opencode/src/session/prompt.ts#L1081-L1130)）；OCR `b17460a6` 虽有可选 plan、main loop 和 review filter，但这是面向代码审查的特定流水线，而非通用任务状态机（[工作流](https://github.com/alibaba/open-code-review/blob/b17460a6a3de8c5f93f693a1f3a0a17a77ed452c/internal/agent/agent.go#L1367-L1507)）。

## 10. 本地工具

所有工具使用手写 JSON Schema，禁止额外字段，并返回统一 envelope：

```json
{
  "ok": true,
  "tool": "read_file",
  "summary": "...",
  "data": {},
  "error": null,
  "truncated": false,
  "duration_ms": 12
}
```

工具参数错误、路径错误和执行失败优先作为内部 tool error 结果回灌，允许模型修正，而不是直接终止整个 Session；Adapter 将其编码为 `is_error=true` 的 Anthropic `tool_result` block。

成功结果满足 `ok=true`、`error=null`；失败结果满足 `ok=false`，并在 `error` 中提供稳定错误码、可读信息和是否可重试，`data` 可携带安全的部分结果。`summary` 始终存在，`truncated` 与成功或失败状态相互独立。未知工具名直接生成 `UNKNOWN_TOOL` 结果，不进入审批。

### 10.1 公共路径边界

- Session 创建时保存 workspace 的 canonical realpath；
- 工具优先使用相对 workspace 的路径；绝对路径只有在最终 realpath 仍位于 workspace 时才允许；
- 访问前解析已有目标或最近存在父目录的 realpath；
- 解析后必须仍位于 workspace 内；
- 指向 workspace 外的符号链接一律拒绝；
- 运行过程中不得改变 Session 的 workspace。

P0 的路径边界面向非对抗性的本地文件系统：执行前必须再次 resolve/校验，并结合 write baseline hash 防止普通外部修改，但不宣称能抵御另一个恶意进程在检查与 open/replace 之间竞态替换目录项。基于 workspace dirfd、逐段 `openat`/`O_NOFOLLOW` 的强 anti-TOCTOU 加固属于 P1。

### 10.2 `read_file`

参数：

- `path: string`
- `offset: integer = 1`，从 1 开始；
- `limit: integer = 800`

行为：

- 只读取 UTF-8 文本文件；
- 默认最多返回 800 行和 40 KiB，任一阈值先到即截断；
- `offset` 使用 1-based 行号，但正文保持原始内容、不添加行号前缀，便于后续精确 `replace`；调用参数中的 `limit` 不得超过配置上限；
- 返回总行数、实际范围、`next_offset` 和 `truncated`；
- 只接受 regular file；目录、FIFO、socket、device、二进制、解码失败和越界均返回结构化错误；
- 无需用户审批。

### 10.3 `write_file`

参数核心：

- `operation: "write" | "replace"`
- `path: string`
- `content` 用于 `write`
- `old_text`、`new_text`、`replace_all=false` 用于 `replace`

行为：

- `write` 创建或整体覆盖 UTF-8 文件，空字符串内容合法；目标父目录必须已经存在，不隐式创建目录；
- `replace` 的 `old_text` 不得为空，默认要求它恰好命中一次；多次命中只有在 `replace_all=true` 时允许；
- 进入审批前生成 diff，冻结全部参数并记录当前文件 hash/不存在状态；
- 新鲜度门槛（read-before-write）：执行前，已存在目标的当前内容必须在本 Session 中被读取过（以 read_file 返回的整文件 sha256 记录，run 层维护 path→hash），且该读取对应的 hash 必须仍等于当前内容——从未读取返回 `READ_FRESH_REQUIRED`（提示先用 read_file 读取最新内容），读取后又被外部修改则沿用 `WRITE_CONFLICT`；新文件与模型自己刚写入的内容（同样记录 hash）无需先读；
- 用户批准后再次核对基线，文件被外部修改则拒绝执行并返回冲突错误；
- 在同目录写临时文件，复制合理的原文件权限，flush/fsync 文件后使用原子替换，并在支持时 fsync 父目录；
- 每次调用均需要审批，除非启动时启用 `--yes`。

整文件写入可能使大文件内容占满模型输出预算。该风险由 `INCOMPLETE_TOOL_CALL` 分流和明确错误提示处理；首版不增加独立 edit/patch 工具。

### 10.4 `run_command`

参数：

- `command: string`
- `cwd?: string`，默认 workspace 根；
- `reason?: string`
- `timeout_seconds: integer = 120`

行为：

- `cwd` 必须位于 workspace；
- 执行非交互 shell 命令，不支持 PTY 或后续 stdin；
- stdout 和 stderr 合并并实时展示；发送给 UI、写入数据库和回灌模型的累计输出统一限制为 40 KiB，超出后继续等待进程但丢弃额外字节，并记录原始字节计数及明确截断标记；
- 默认超时 120 秒；
- 超时或用户停止时 best-effort 终止当前进程组：先 TERM，3 秒后仍未退出则 KILL；主动 `setsid`/daemonize 脱离该进程组的后代不在 P0 强保证范围；
- 子进程采用环境白名单：默认只传必要的 `PATH`、locale、临时目录，并使用隔离 HOME；其它变量必须由本地未入库配置显式 allowlist，配置指定的模型 API key 永远禁止透传；
- 每次调用均需要审批，除非启用 `--yes`。

`run_command` 不是安全沙箱。批准的命令仍拥有当前操作系统用户权限，UI 和 README 必须明确提示这一点。

### 10.5 工作区指令（AGENTS.md）与技能（skills）

参考 OpenCode 的简化模式（技能不自动进入上下文，模型看到索引后按需读取；目录名约定不同：本实现使用 `.agents/skills/`）。

**AGENTS.md 自动加载**：

- 每次 run 开始时（不是 Session 创建时，因此两次 run 之间的修改在下一次 run 生效）读取工作区根目录的 `AGENTS.md`（大小写敏感，也接受小写 `agents.md`；其它大小写不识别）；读取经由与工具相同的 workspace 路径边界；
- 内容以 `## Workspace instructions (AGENTS.md)` 小节附加到编译后的 system 提示末尾，成为 §7.2 意义上的不可压缩 mandatory 内容，永远不会被裁剪或摘要；
- 超过 128 KiB 截断并附加明确标记；缺失、不可读、非 regular file 或指向 workspace 外的 symlink 一律视为不存在，不报错、不附加。

**技能（on-demand skills）**：

- 约定：`<workspace>/.agents/skills/<skill-name>/SKILL.md`，目录内可捆绑伴生文件（脚本、参考文档）；只扫描一层子目录，不递归；
- SKILL.md frontmatter（两个 `---` 行之间的 `key: value` 行）必须包含 `name`（小写字母/数字/连字符，且等于目录名）与 `description`（1-1024 字符）；无效或缺失的技能被跳过，并发布 `skill.invalid` 诊断事件（含目录、错误码与原因），run 不失败；
- 每次 run 开始时（与 AGENTS.md 同一阶段）扫描一次；系统提示追加紧凑的 `## Available skills` 索引（每技能一行 `- name: description`，加一行加载指引），索引常驻上下文，正文不常驻；
- 第 4 个模型可见工具 `skill`（只读、无需审批、参数 `name: string`、`mode: "read" | "list"`，默认 `read`）：
  - `read` 返回完整 SKILL.md 正文（frontmatter 之后）与技能目录伴生文件清单（workspace 相对路径 + 字节数）；模型用 `read_file` 自行读取伴生文件，路径边界无需例外；
  - `list` 返回索引（名称、描述、文件数）；
  - 未知技能名返回 `UNKNOWN_SKILL` 工具错误，模型可自行纠正；
- 技能目录的修改在下一次 run 的扫描中生效。

## 11. 审批与工具执行顺序

1. 完整 assistant/tool calls 先持久化；
2. 多个调用按模型给出的顺序串行处理；
3. `read_file` 自动执行；
4. `write_file` 展示 diff、操作类型和目标路径；
5. `run_command` 展示完整命令、cwd、理由、超时和非沙箱警告；
6. Approval 只能引用后端冻结的调用，浏览器不能修改参数；
7. `Approve once` 只批准当前调用；
8. `Reject` 为当前调用生成 rejected tool result，并为本批剩余调用生成 skipped tool results，然后让模型重新规划；
9. `Stop` 取消整个 run；尚未取得 effect-start 的当前调用补 cancelled result，后续 queued 调用补 skipped result，已开始的调用等待取消/完成并按实际状态补结果；
10. `--yes` 自动批准写入和命令，但仍记录完整审批事件，并在 UI 显示醒目的受信任模式状态。

同一批存在多个 tool calls 时，数据库记录其原始顺序及逐项状态。Run 的 `AWAITING_APPROVAL` 或 `TOOL_RUNNING` 始终指向当前调用；后续调用保持 `queued`。Reject 将当前调用标成 `rejected`、后续调用标成 `skipped`；用户 Stop 将尚未取得 effect-start 线性化点的调用标成 `cancelled`、后续 queued 调用标成 `skipped`，已经开始的当前调用则按实际结果标成 `succeeded`、`failed`、`cancelled` 或 `unknown`。

Approve/自动批准只表示允许尝试执行，不等于副作用已经开始。Coordinator 在执行前必须通过条件事务 `begin_effect`：同时验证审批仍有效、Run 未请求取消、当前调用仍为 queued/approved，并写入 `effect_started_at` 与 `TOOL_RUNNING`。若 Stop 先进入 `CANCELLING`，旧审批处理器不得再启动工具；若 `begin_effect` 先成功，Stop 只能请求取消正在运行的工具。write 已完成原子 replace 时记录 `succeeded`，不能因随后 Stop 改写为 `cancelled`；进程或写入状态因崩溃无法确认时记录 `unknown`。

## 12. 中断、重试和恢复

### 12.1 用户停止

- 接受 Stop 时先在 SQLite 中写入 `cancellation_requested_at`、`state=CANCELLING` 和 durable event，再触发内存取消令牌；重复 Stop 返回同一结果；
- 模型流：取消当前请求；已显示的半截文本存为 UI 可见的 `interrupted` 记录，但不进入后续模型上下文；
- 等待审批：取消当前及未处理调用并补齐 tool results，再将配对完整的消息组转为 committed；
- 命令执行：终止进程组并保存截断到取消时的输出；
- 停止后 run 为 `CANCELLED/USER_STOP`，Session 回到 IDLE，可继续多轮对话。

### 12.2 模型请求重试

官方 SDK 自动重试关闭，项目请求层是唯一重试所有者。

- 可重试：HTTP 408、409、429、5xx（显式包括 529 overloaded）、连接失败、连接重置和读超时；
- 不重试：401/403、配置错误、明确的协议错误；
- 先采信 `x-should-retry: false|true`；延迟依次解析 `retry-after-ms`、数值秒或 HTTP-date `Retry-After`，仅接受不超过配置上限 60 秒的合法值，非法/过大值回退本地退避；
- 无响应头时使用 2 秒起始的指数退避，加 25% jitter，30 秒封顶；
- `max_attempts=5` 表示包含首次请求在内最多尝试 5 次；
- 等待期间持续发布可见的 attempt 和下一次重试时间，Stop 可以立即取消等待；
- 流中断时丢弃未提交 draft 并重新发起本次模型调用；此时尚未执行工具，不会重复本地副作用。

模型返回上下文超限时，先触发一次压缩并重试；压缩后仍失败才记为 `CONTEXT_OVERFLOW`。

### 12.3 浏览器断线

- 浏览器断线或刷新不取消后端 run；
- 重连后发送 Session 快照和遗漏的 durable events；
- 审批状态恢复同一张固定审批卡；
- 没有浏览器在线时绝不自动批准写入或命令。

### 12.4 服务重启

- 启动时将遗留活动 run 标记为 `INTERRUPTED/SERVER_RESTART`；
- 不自动重放任何可能有副作用的工具；
- 若重启发生在 `TOOL_RUNNING`，当前调用标为 `unknown` 并补充“执行状态未知，请检查 workspace”的结果，后续 queued 调用标为 `skipped`；
- 若重启发生在 `AWAITING_APPROVAL`，说明工具尚未执行，当前和后续调用均标为 `cancelled`；
- 补齐所有合成结果后将该 assistant/tool 组转为 committed，确保用户继续对话时历史合法；
- 若中断时存在可能仍在运行或已产生副作用的命令/写入，Session 进入 `requires_recovery_ack`，禁止新 run；UI 明确提示“进程可能仍在运行，请人工检查 workspace/进程”，用户确认后才允许继续。P0 不宣称可以在非容器 POSIX 环境可靠回收崩溃后脱离的任意后代进程；
- 用户确认恢复风险后继续发送消息，由 Agent 先检查文件和测试状态再决定后续操作。

### 12.5 不可恢复错误

401/403、配置错误、重试耗尽、协议无法归一化和压缩后仍超窗进入 `FAILED`。完整历史、错误类别、重试次数和停止原因保留；修复配置后仍可在同一 Session 继续。

## 13. Web UI

采用接近 Codex 桌面端的 Developer Workbench：

- 左栏：新建 Session、当前 workspace、历史 Session 与恢复入口；
- 中栏：用户/助手消息、工具事件时间线、固定审批区和输入框；
- 右栏：当前运行状态、模型、会话累计的运行次数/轮次/重试与 Token 用量（跨全部运行累加，不随新请求清空）、上下文占用、已加载上下文（AGENTS.md 与技能按会话并集）、文件变化与停止原因；
- 窄屏隐藏右栏并改用抽屉，不实现复杂移动端布局。

### 13.1 输入框状态

- IDLE：输入框右下角显示 Send；
- 用户发送后：同一位置原位切换为 Stop；
- STARTING、BUILDING_CONTEXT、COMPACTING、MODEL_STREAMING、RETRY_WAIT、AWAITING_APPROVAL 和 TOOL_RUNNING 状态均保持 Stop；`CANCELLING` 显示禁用的“正在停止”；
- run 结束、失败或取消后恢复 Send；
- 运行时允许编辑并保留下一条草稿，但不排队发送。

### 13.2 固定审批区

- 待审批工具固定停靠在输入框正上方，不随消息列表滚动；
- 因工具串行执行，同一时刻最多显示一张审批卡；
- 审批卡展示冻结参数；write 显示 diff，command 显示命令、cwd、理由、超时和风险；
- Approve、Reject 或 Stop 后，审批卡从固定区消失，并归档为对话中的普通工具事件；
- 刷新或重连后，未决审批卡恢复在相同位置。

### 13.3 状态展示

工具卡至少区分：等待审批、运行中、成功、失败、拒绝、取消、跳过。模型层至少区分：流式生成、压缩、等待重试、已停止和不可恢复错误。详情默认折叠，避免演示界面被日志淹没。

重启后恢复 Session 时，前端显示“上一 run 因服务重启而中断”的历史横幅。若没有未知副作用，输入框处于 IDLE 并允许继续；若 `requires_recovery_ack=true`，输入框保持禁用并要求用户先确认已检查 workspace/进程。这与仍在运行、正在自动重连的状态明确区分。

## 14. 前后端协议

P0 REST 用于 bootstrap/健康检查、公开配置、目录浏览、Session 创建/列表和初始快照；Session 重命名/删除与 JSONL 导出属于 P1。WebSocket 用于一个 Session 的实时双向控制与事件流。`GET /api/bootstrap` 返回当前进程生命周期内有效的 CSRF/session token 和公开连接信息；token 不写 SQLite、日志或浏览器持久存储。

生产启动时由 FastAPI 托管 `web/dist`，完成前端构建后只需保留一个服务进程。开发模式下使用 Vite dev server，并把 `/api` 与 WebSocket 代理到 FastAPI。

客户端命令至少包括：

- `session.subscribe`
- `run.start`
- `run.stop`
- `approval.resolve`
- `session.ack_recovery`
- `session.compact`

每条客户端命令携带 `client_command_id`，后端以此去重，避免断线重发导致重复 run 或重复审批。服务端 durable event 包含 `session_id`、`run_id`、`seq`、`type`、`payload` 和时间戳；snapshot 额外携带 `snapshot_seq`，瞬时 delta 携带 `run_id` 和 draft epoch。

`run.start`、`run.stop` 和 `approval.resolve` 的 command receipt、payload hash、领域状态变更与 durable ACK/event 必须处于同一 SQLite 事务。收到相同 Session、相同 `client_command_id` 的重复命令时，不再次执行：`completed` 返回首次 ACK；`processing` 返回同一 resource ID 和处理中状态；同一 id 对应不同命令内容时返回冲突错误。禁止先独立 claim command、再在另一个事务执行领域变更。

`session.compact` 是无 run 的维护压缩：仅当没有任何活动 run 时可用（否则以命令错误拒绝——正在运行的 loop 自己的 builder 拥有压缩决策权）；其 command receipt、活动 run 拒绝与 session 级 durable event `compaction.started` 在同一 SQLite 事务，随后压缩器按 §7.4 的强制触发路径执行，`compaction.finished` 携带 `{before_estimated_tokens, after_estimated_tokens, forced}`（失败时附 `error.code` 且快照保持不变）收尾。压缩生命周期事件对 run 内自动压缩同样生效：`compaction.started`/`compaction.finished` 锚定在 run 的 COMPACTING 阶段上，run 内自动触发时 `forced=false`。

生产模式只接受同源请求；FastAPI 校验 `Host` 为 `127.0.0.1`/`localhost` 和实际端口，WebSocket 校验 `Origin`。开发模式只额外允许显式配置的 loopback Vite origin。所有改变状态的 REST/WS 命令还需携带启动时生成、仅通过同源 bootstrap 暴露的随机 CSRF/session token；即使启用 `--yes` 也不绕过这些检查。服务重启后旧 token 失效，WS 以专用认证 close code 拒绝；前端清除内存 token、重新请求 bootstrap，再执行 subscribe/snapshot 恢复。

目录选择器由本地后端列出服务端目录；浏览器不上传整个目录。用户选中后后端验证目录存在、可访问并保存 canonical realpath。若启动时传入 `--workspace`，它成为初始 Session 的目录；以后仍可通过网页为新 Session 选择其它目录。

## 15. 配置与启动

公开仓库提交 `config.example.toml`，默认读取启动目录下的 `config.toml`，也可通过 `--config` 指定其它路径；本地 `config.toml` 必须忽略。配置中只保存 API key 的环境变量名，不保存实际凭据。

```toml
[server]
port = 8000
open_browser = true

[model]
base_url = "https://api.anthropic.com"
model = "claude-model-name"
api_key_env = "ANTHROPIC_API_KEY"
context_window = 64000
max_output_tokens = 8192
stream = true

[agent]
max_rounds = 30
tool_argument_retries = 2
doom_loop_threshold = 3

[context]
compact_trigger_ratio = 0.80
compact_target_ratio = 0.60
safety_margin_tokens = 2048
summary_max_tokens = 16384
recent_turns_min = 2
recent_budget_ratio = 0.40

[retry]
max_attempts = 5
initial_delay_seconds = 2.0
max_delay_seconds = 30.0
jitter_ratio = 0.25

[tools]
read_max_lines = 800
read_max_bytes = 40960
command_timeout_seconds = 120
command_output_bytes = 40960
kill_grace_seconds = 3
pass_env = []

[evaluation]
judge_max_output_tokens = 4096
```

启动时校验：模型名和 URL、指定环境变量、窗口与输出预算关系、`stream=true`、`0 < compact_target_ratio < compact_trigger_ratio < 1`、正数且小于 context window 的 `summary_max_tokens`、`max_rounds >= 2`、正数超时和 workspace。错误应指出具体字段和修复方法，但不得输出密钥值。监听地址固定为 `127.0.0.1`，不接受配置覆盖。

配置优先级为：CLI 参数 > `config.toml` > 内置默认值。模型配置不热更新；修改后重启服务后，即使打开旧 Session，新 run 也使用新配置重新构造模型视图，旧 run 的配置快照和历史保持不变。

标准运行方式：

```bash
uv venv .venv --python 3.12
uv sync --frozen
npm --prefix web ci
npm --prefix web run build
export ANTHROPIC_API_KEY="..."
uv run --python 3.12 coding-agent serve \
  --config config.toml \
  --workspace /path/to/project \
  --open
```

### 15.1 Makefile 统一入口

公开仓库根目录提供 `Makefile` 作为安装、开发、测试和启动的统一快捷入口。Makefile 只负责编排项目自身命令，不绕过 `uv`、`npm` 或正式 CLI；README 同时保留底层等价命令，便于定位问题。所有目标声明为 `.PHONY`，任一子命令失败时立即返回非零退出码。

|---|---|
| `make help` | 列出可用目标、用途和可传入变量，作为默认目标 |

| `make build` | 执行 `npm --prefix web run build`，生成由 FastAPI 托管的 `web/dist` |

| `make dev-api` | 启动 FastAPI 开发后端，不隐式启动或管理前端进程 |
| `make dev-web` | 启动 Vite 开发服务器，并由 Vite 代理 `/api` 与 WebSocket |
| `make test-backend` | 通过 `uv run --python 3.12 pytest` 运行后端单元与集成测试 |
| `make test-frontend` | 通过 `web/package.json` 的 `test` script 运行前端组件测试 |
| `make test` | 顺序执行 `test-backend` 和 `test-frontend`；默认不访问真实模型网络 |

启动参数通过 Make 变量传递，默认配置文件为 `config.toml`；`ARGS` 原样追加到正式 CLI，因此仍由 CLI 完成参数校验：

  ARGS='--workspace /path/to/project --open'
```

开发模式使用两个终端，避免 Makefile 引入额外的进程管理依赖，并确保任一服务的日志和退出状态清晰可见：

```

API key 仍只能通过环境变量提供，禁止作为 Make 变量或 `ARGS` 写入命令。Makefile 不提供 `clean`、`distclean` 等删除目标；临时产物处理继续遵守项目的禁止 `rm` 约束。`make test` 和 `make check` 均不包含 `tests/live/`，真实模型测试仍须通过 `RUN_LIVE_TESTS=1` 显式启用。

CLI 参数：

- `--config PATH`
- `--workspace PATH`
- `--data-dir PATH`，覆盖默认 SQLite/运行数据目录，供测试和评测隔离；
- `--port PORT`
- `--open`
- `--yes`

该命令仍执行正式的模型适配器、上下文、工具和 SQLite 流程，只省略浏览器；测试 UI 的职责由 Playwright E2E 单独承担。

## 18. 量化评测

### 18.1 目标与边界

评测必须区分两件事：自动化测试证明实现是否符合契约；真实模型评测衡量在固定任务集上的效果、成本和稳定性。两者不能混为一谈，模型声称“已完成”也不能作为成功依据。

评测器只负责准备任务、调用本项目、收集事件并运行确定性 oracle，不包含第二套 Agent Loop，不引入外部 Agent 框架。它通过正式的 headless CLI 或 API 边界驱动产品，确保评测的是实际交付路径。

P0 只要求 `run-v1` 运行报告、4 个公开小任务各 1 次的 smoke 和一份脱敏汇总，用于证明工具、token、时长和完成结果可采集。以下 12×3 campaign、控制变量、消融和外部 benchmark 均为 P1；只有 P0 主链、README.txt、视频和表单材料已可提交后才执行。

### 18.2 公开与私有内容拆分

```text
my-coding-agent/                   # 公开交付仓库
├── src/coding_agent/evaluation/   # runner、评分与报告代码
├── evaluation/
│   ├── README.md
│   ├── schemas/
│   ├── tasks/public/
│   └── examples/                  # 脱敏示例结果
└── src/coding_agent/              # 指标采集与 run report 导出

<private-workspace>/               # 仓库外私有工作区
└── evaluation/
    ├── manifests/
    ├── tasks/private/
    ├── results/raw/               # 默认 gitignore
    └── reports/                   # 可追踪的脱敏汇总
```

公开仓库保存通用 runner、schema、评分代码、少量可重新分发的公开任务和示例报告。仓库外私有工作区保存隐藏任务、真实 campaign 配置、原始 transcript 和完整结果。SQLite 仍是单次 Agent 运行的事实源；评测 JSONL/CSV 是只读导出和派生结果，不参与运行恢复。

为避免评测污染日常会话，每个 run 必须使用独立临时 workspace 和 `--data-dir`，不得复用用户的默认数据库。原始 prompt、工具参数、文件内容和本地绝对路径可能敏感，默认结果目录不提交；公开报告只包含脱敏聚合值。

### 18.3 P1 可参考的公开 benchmark

| Benchmark | 已核实特点 | 本项目用法 |
|---|---|---|
| [SWE-bench](https://github.com/SWE-bench/SWE-bench/tree/7a21e05772954cc81471ae19d56f436cecf43c54) | ICLR 2024 Oral；真实 GitHub issue；当前官方文档列 Full 2,294、Lite 534、Verified 500；官方 harness 使用 Docker | **首选外部权威验证**。从 Verified 预注册 3 个实例，用官方 harness 评分 |
| [Aider Polyglot](https://github.com/Aider-AI/polyglot-benchmark/tree/7e0611e77b54e2dea774cdc0aa00cf9f7ed6144f) | 基于 Exercism，约 225 个多语言小任务，运行快、判定清晰 | 可选 1–3 个 Python/JavaScript smoke，验证小型编辑能力 |
| [BugsInPy](https://github.com/soarsmu/BugsInPy) | 当前仓库包含 17 个 Python 项目的 501 个真实 bug，支持 checkout/test | 适合后续补充 Python 修复任务；旧依赖环境和根仓库无统一许可证声明增加成本 |
| [Terminal-Bench](https://github.com/harbor-framework/terminal-bench-1) | 真实终端任务，Apache-2.0，官方 harness 依赖 Docker/Harbor | 与命令型 Agent 相似，但范围和环境成本过大，不纳入首版 |

SWE-bench harness 代码使用 MIT 许可证，但各任务所引用的上游仓库仍服从各自许可证。BugsInPy 和 Aider Polyglot 没有适用于整个任务仓库的统一许可证声明。因此首版不复制完整第三方数据集，只在 manifest 中保存来源 URL、固定 revision、instance ID 和 hash，运行时按官方方式获取。

SWE-bench 官方支持按 `instance_id` 运行少量样本。选择流程必须在模型运行前完成：先依据仓库差异、难度、资源和预计测试时长筛选，再用 gold patch 验证环境，最后冻结 3 个不同仓库的 Verified instance。gold patch、test patch 和 oracle 不得出现在 Agent workspace 或模型上下文中。报告只能写“固定 SWE-bench Verified 子集 resolved x/3”，不得包装成完整 SWE-bench 分数或与官方排行榜直接比较。

官方 SWE-bench Docker 环境资源开销较高，当前文档建议约 120 GB 可用磁盘、16 GB RAM 和 8 CPU，ARM64 支持仍有限。因此它是首版完成后的外部 smoke，而不是日常回归测试或核心交付阻塞项。正式使用时固定 harness tag `v5.0.1`、任务仓库 revision、instance IDs、镜像和 run ID；同一 instance 的不同 patch 必须使用不同 run ID，避免官方缓存复用旧结果。

### 18.4 P1 自建主评测集

P1 主评测使用 12 个小型、可完全控制的任务，四类各 3 个；P0 先从四类各选 1 个公开任务运行 1 次：

1. 新建单文件功能；
2. 对已有函数做 1–5 行局部修改；
3. 搜索定位后修改两个文件；
4. 在 600 行以上文件中完成小改动。

每个 task manifest 至少记录：

- `schema_version`、`task_id`、类别和原始 prompt；
- 只读 baseline 的来源与 tree hash；
- 允许修改与禁止修改的路径；
- P0 自动批准 smoke 的精确 command/cwd allowlist；
- Agent 总超时；
- 外部 oracle 入口及其 hash；
- 预期 baseline 失败、gold patch 成功。

模型运行前必须自动验证 baseline 至少有目标断言失败、gold patch 通过、可选错误变体失败。任何一项不满足则记为 `HARNESS_SETUP`，停止该任务，不得把它计作 Agent 失败。

每次运行：

1. 从固定 baseline 生成全新临时 workspace；
2. 使用独立临时 SQLite/data directory；
3. 只有操作者在 dry-run 后显式传入 `--yes --ack-unsafe-auto-approve` 才允许无人审批执行，并使用隔离 HOME 与环境白名单；评测不设命令 allowlist，agent 可自由使用命令；
4. Agent 结束后记录文件树 hash 和 diff；
5. 在 workspace 外运行隐藏 oracle；
6. 保存不可变的 run 结果，禁止覆盖同名 campaign/run。

P0 不是恶意代码安全沙箱。临时目录、命令 allowlist、隔离 HOME 和外部 oracle 只能降低意外污染，不能声称能够防御恶意模型代码；P1 的大批量无人值守 campaign 应放入一次性容器或低权限隔离环境。

### 18.5 成功定义与指标

主指标 `strict_success` 必须同时满足：

```text
目标 oracle 通过
+ 原有回归测试通过
+ 无 protected/forbidden 路径改动
+ 无 manifest/canary 检测到的 workspace 越界或禁止路径修改
+ run 正常以 COMPLETED 结束
```

另行报告 `artifact_correct`，表示代码和测试结果正确但 run 因 `MAX_ROUNDS` 等原因未正常结束，避免把产物质量和 Agent 控制质量混为一谈。

| 类别 | 指标 |
|---|---|
| 正确性 | strict success、artifact correctness、run 成功率、每任务 3 次成功比例、至少 2/3 成功的 robust task 数 |
| 模型 | main/compaction 请求数、attempts、input/output/cache creation/cache read tokens、usage 覆盖率 |
| 工具 | proposed/executed/succeeded/failed/skipped 次数、各工具次数、重复调用、输出字节与截断 |
| 上下文 | 压缩次数、压缩前后 token、pruned bytes、摘要 token、`compaction_above_target`、估算/实际误差、压缩失败、压缩后重复读取/调用 |
| 时长 | Agent wall time、模型请求、工具执行、重试等待、压缩、oracle 时间 |
| 修改 | 修改文件数、增删行、禁止路径修改率、写入冲突、canary 检测到的越界 |
| 稳定性 | stop reason、error kind、网络重试、协议错误、上下文溢出 |

Token 比较只使用 API 返回的 usage；缺失时记为 `null` 并报告 usage coverage，不能拿本地估算冒充真实消耗。Anthropic usage 分别保留 `input_tokens`、`output_tokens`、`cache_creation_input_tokens` 和 `cache_read_input_tokens`，不能假设缓存 token 已包含于某个通用 prompt 总数。成本只有在价格表版本以及模型对应的常规输入、cache write/read 和输出计费语义均明确时计算，缺任一必要字段则为 `null`。

```text
cost = input_tokens × input_price
     + cache_creation_input_tokens × cache_write_price
     + cache_read_input_tokens × cache_read_price
     + output_tokens × output_price
```

所有时长使用 monotonic clock。Agent wall time从接受用户任务到 run 终态，包含模型、工具和重试等待；workspace 准备与 oracle 时间单独报告。

失败分类固定为 `harness_setup`、`harness_oracle`、`model_auth`、`model_transport`、`model_protocol`、`model_refusal`、`pause_turn`、`context_overflow`、`output_truncated`、`max_rounds`、`doom_loop`、`tool_argument`、`tool_path`、`tool_execution`、`command_timeout`、`write_conflict`、`forbidden_modification`、`oracle_failure` 和 `unknown`。每次失败同时记录 `failure_stage = setup | model | agent | tool | oracle`。

### 18.6 P1 重复、控制变量与汇总

- 每个任务、每种配置运行 3 次；12 个任务即每组 36 次；
- 相同任务和 repeat 编号组成配对样本；组间使用预先固定的交错顺序，减小模型服务漂移与缓存影响；
- 同一比较只改变一个变量，并固定 Agent commit、模型、请求参数、system prompt、工具 schema、任务 revision、超时和 `max_rounds`；
- 每次运行保存 `agent_commit`、`task_hash`、`config_hash`、`prompt_hash`、`tool_schema_hash`、模型标识和时间戳；
- 报告原始 `passed/n`、均值、中位数、范围和总体 p95；小样本不宣称统计显著；
- `HARNESS_SETUP` 和 `HARNESS_ORACLE_ERROR` 不混入 Agent 能力失败，但必须保留并同时报告“启动总数”和“有效运行数”；
- 每类失败至少人工阅读一条 transcript，不删除不利结果。

`task_completion_rate = strict_success_runs / valid_runs`。一个任务 3 次中至少成功 2 次才计入 `robust_task_count`；同时保留每个任务的三个原始布尔结果，不能只展示平均数。

单次结果使用版本化 `run-v1` JSON，至少包含 task/repeat、各类 hash、Agent commit、模型标识、`strict_success`、`artifact_correct`、run state、stop reason、failure stage、模型调用与 token、工具调用、各阶段耗时、diff 和 oracle 结果。campaign 同时生成 `runs.jsonl`、`summary.json`、`summary.csv` 和 `report.md`。`args_hash` 对 canonical JSON 排序后计算，公开报告不包含原始工具参数或 workspace 绝对路径。

### 18.7 P1 压缩专项消融

使用同一模型、任务、prompt、工具和顺序比较：

- C0：关闭压缩；
- C1：只确定性裁剪旧 tool output；
- C2：裁剪 + 本项目结构化摘要。

通过较小的模拟 context window 或要求读取 5 个以上文件的任务确保每组确实触发压力。若某组没有触发预期压缩，该组实验判为无效而不是解释为“没有差异”。

除成功率、token 和 wall time 外，专项记录：所有 user 原文逐字节保留率、约束违反数、压缩后重复读取同一路径次数、重复工具指纹、摘要调用成本和 `CONTEXT_OVERFLOW`。若 C2 相对 C1 增加超过 25% token 且不提高完成率，应提高触发阈值、缩小摘要或暂时只使用 prune。

### 18.8 评测 CLI

公开仓库提供独立入口，但复用正式 Agent Core：

```bash
uv run --python 3.12 coding-agent-eval validate \
  --manifest evaluation/tasks/public/manifest.toml

uv run --python 3.12 coding-agent-eval run \
  --manifest evaluation/tasks/public/manifest.toml \
  --repeats 1 \
  --serial \
  --out /path/to/private/results

uv run --python 3.12 coding-agent-eval summarize \
  --input /path/to/private/results
```

Evaluator 为每个任务启动独立的 headless Agent 进程，通过正式应用入口运行，不直接调用私有 helper，也不包含自行规划逻辑。真实模型运行前提供 `--dry-run`，展示任务数、预计最大请求数、工作目录和输出位置。

## 19. 安全与公开仓库边界

- 公开交付主体是独立仓库 `my-coding-agent/`；私有规划工作区可以用 submodule 记录其 commit 指针，但该私有仓库的名称、内容和历史不属于交付物；
- 开发阶段内层仓库可保持 Private，但最迟在首次正式提交表单前完成全历史审计、改为 Public，并从未登录/无权限环境验证 URL 可访问；可见性切换不得迁移、squash 或改写提交历史。题目“公开仓库”是否要求开发全程公开存在解释空间，因此发布 gate 必须保存仓库创建时间、首次提交和转公开时间的核验记录；
- `my-coding-agent/doc/` 只公开本设计方案和实施计划；题目原文、调研素材、视觉讨论源文件和内部工作记录继续保存在仓库外；
- `.superpowers/`、`tmp/`、`.venv/`、`config.toml`、SQLite、日志、`node_modules/`、前端构建产物和测试报告全部忽略；
- 公开仓库只提交评测框架、schema、可再分发的公开样本和脱敏示例；完整任务集、原始 transcript 与真实运行结果位于仓库外私有工作区；
- API key 仅来自环境变量，后端日志、异常、网页和配置快照只显示环境变量名或“已配置”；
- 公开代码、fixture、截图和视频不得包含内部 URL、项目路径、代码、工号或其它内部痕迹；
- 提交前扫描当前文件和完整 Git 历史中的 key/token/password；
- 若凭据曾进入提交历史，不能只删除文件，必须立即作废并更换；
- 非破坏性本地 Git 开发操作已预授权，包括暂存、commit、本地分支和 worktree 管理；commit message 只能客观描述项目变更，不得包含 AI/模型辅助署名、生成来源或 `Co-authored-by`/coauthor trailer。任何 push、远端分支/tag 写入、PR/MR 或 Release 仍须逐次取得用户明确授权，本地 commit 不构成 push 授权。

## 21. 验收标准

P0 完成必须同时满足：

1. 用户可从网页创建 Session，选择 workspace，并进行多轮对话；
2. 也可通过 `--workspace` 启动初始 Session；
3. 模型能使用本地工具（含按需 `skill`）完成真实的小型编程任务；
4. 写入和命令默认需要审批，审批参数不可被前端篡改；
5. Send 在活动 run 中原位变为 Stop，审批固定显示在输入框上方；
6. 页面刷新不终止 run，服务重启不重放副作用；
7. 网络错误按可见策略重试，用户可在等待时停止；
8. 完整历史可从 SQLite 恢复，压缩不改变原始历史；
9. 达到上下文阈值时保留所有 user 原文、结构化 rolling summary 和最近完整轮次，并在 mandatory 内容高于 60% 时采用可解释的软目标；
10. 替换符合约定的 Anthropic-compatible Messages 服务或模型配置后无需修改代码；首版不支持 OpenAI Chat Completions 或其它第二协议；
11. 默认自动化测试不访问网络，关键状态与边界均有确定性覆盖；
12. 基础评测可在全新 workspace/data directory 中运行 4 个公开小任务各 1 次，并生成版本化 run JSON 和脱敏汇总；
13. 公开仓库、README 和视频中不存在凭据或内部素材；
14. 内层仓库已公开且无需登录即可访问，最终“姓名.zip”校验通过并已上传指定表单、保存回执。

P1 在 P0 稳定且交付材料已经可提交后继续：扩展到 12 个自建任务 × 3 次、JSONL/CSV/Markdown 完整 campaign、压缩消融、SWE-bench smoke、`pause_turn` continuation、非流式模型兼容和其它增强功能。P1 失败不得阻塞 P0 仓库、README.txt、视频与表单提交。
